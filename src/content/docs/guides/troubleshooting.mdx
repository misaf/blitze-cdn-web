# Troubleshooting

Use this page to diagnose a failed command, deployment, or certificate action.
Work from the controller outward: local configuration, inventory, SSH, then edge
state.

## Before you begin

Preserve the deployment record, retained output, audit tail, and relevant
controller or edge logs before retrying. Redact keys, private material,
hostnames, addresses, and certificate paths before sharing diagnostics. Never
delete a live deployment lock to make an error disappear.

## Collect diagnostics

```bash
blitzecdn --verbose doctor
blitzecdn --verbose validate
blitzecdn status --limit 5
blitzecdn audit --limit 20
```

Use `--json` when collecting structured output for automation. Remove API keys,
private keys, inventory addresses, and sensitive deployment output before
sharing diagnostics.

<Details>
  <Summary>Advanced: collect structured records for an incident</Summary>

Keep the original JSON files read-only and redact copies before sharing:

```bash
blitzecdn --log-json doctor --json > doctor.json
blitzecdn status --limit 20 --json > deployments.json
blitzecdn audit --limit 100 --json > audit.json
```

Record the controller time, command exit codes, affected deployment IDs, and
whether an external edge probe succeeded. Never attach `.env`, private keys,
or raw inventory to an incident report.

</Details>

<Callout type="warning">
  Do not delete a lock, disable SSH host-key checking, or retry a timed-out
  deployment until you have determined whether a process or remote convergence
  is still active.
</Callout>

## Authentication

- **503:** configure `BLITZE_API_KEYS`; malformed or short keys fail at startup.
- **429:** ten failed authentications from one client address within a minute
  throttle it. Behind a reverse proxy this counts all clients together — see
  [Production](/docs/guides/production).

## Inventory and SSH

- **Inventory missing:** create `ansible/inventory/hosts.yml` or set
  `BLITZE_INVENTORY` to an absolute path.
- **SSH host-key failure:** validate the new fingerprint out of band; never
  bypass host-key checking.
- **Group variables ignored:** `group_vars` must sit beside the inventory file in
  `ansible/inventory/group_vars/`. Elsewhere Ansible silently skips it and roles
  fall back to their defaults.

## Firewall

- **Firewall assertion:** provide at least one trusted CIDR containing the current
  management source before retrying. An empty `blitzecdn_firewall_ssh_sources`
  deliberately fails closed.

## Deployment lifecycle

- **Nginx validation failure:** inspect bounded stderr/status, correct desired
  state, plan, and deploy. Nginx is not reloaded after a failed validation.
- **Deployment conflict:** inspect the current controller process and the lock
  owner. Do not delete a live lock file; filesystem locks release when their
  process exits.
- **Timeout:** confirm network and package-repository health and host state. A
  timeout is not proof that no remote changes occurred; rerun `plan` before
  retrying. On timeout the controller signals the whole `ansible-playbook`
  process group (`SIGTERM`, then `SIGKILL` after five seconds), so per-host
  workers stop rather than converging edges after the run is recorded as timed
  out.
- **Stuck `queued`/`running`:** API deployments run on a worker thread, so the
  record only settles when Ansible finishes. If the controller was restarted
  mid-run, startup marks the record `abandoned`; rerun plan before retrying.

## Storage

- **Disk exhaustion:** stop new work, preserve the database, free space outside
  `.state`, run SQLite integrity checks, then validate before deployment.

## Certificates

- **ACME request failure:** confirm every requested hostname resolves to the edge
  addresses, port 80 is public, the HTTP-only site was deployed first, Certbot is
  installed on the controller, and all edges are reachable over SSH.
- **Certificate upload failure:** provide an unencrypted PEM private key and a PEM
  chain whose leaf SANs cover every configured site hostname.

## Verify recovery

After correcting the cause, run `validate` and `plan`. Require a successful plan
before applying. After deployment, inspect the deployment record and probe the
affected hostname through an edge. Do not treat a successful local health check
as proof that remote traffic is healthy.
