# API usage

Use the HTTP API to automate site changes, deployments, certificates, and audit
reads. Every route except `GET /health` requires an `X-API-Key` header. See the
[HTTP API reference](/docs/reference/api) for complete routes and models.

## Before you begin

- Configure at least one API key.
- Start the API on loopback first.
- Put authenticated TLS in front of the API before exposing it over a network.

## Operators and keys

Operators authenticate with API keys; they are not authorization roles. Secrets
are set via environment (or a secret manager), never as CLI arguments or TOML.
Use the [API key rotation procedure](/docs/guides/api-key-rotation) for planned
rotation or suspected disclosure.

- `BLITZE_API_KEYS` — comma-separated `operator:secret`. Each secret needs at
  least 32 characters; duplicate operators are rejected.
- `BLITZE_API_KEY` — a single unnamed key, registered as operator `default`.

Authentication failures are throttled: ten failed authentications from one
client address within a minute return `429`. Behind a reverse proxy this counts
all clients together.

## Serving

```bash
blitzecdn serve                 # binds 127.0.0.1:8000 by default
blitzecdn serve --host 0.0.0.0 --port 8443
```

<Callout type="error">
  The default bind is loopback. Before binding to a non-loopback address, put an
  authenticated TLS proxy in front of the API and keep the application port off
  the public internet.
</Callout>

## Lifecycle of a mutation

Reads are synchronous. Mutations follow the pattern:

1. `POST /v1/deployments` (or `/v1/rollbacks`) returns `202 Accepted` with a
   queued `Deployment` record.
2. Poll `GET /v1/deployments/{id}` until `status` settles on `succeeded`,
   `failed`, `timed_out`, or `abandoned`.

A convergence outlives any HTTP client, so `202` with polling is the correct
shape rather than a blocking request.

## Common workflows

Set the base URL and key once. Keep the leading space if your shell is configured
not to save space-prefixed commands in history:

```bash
 API_KEY='replace-with-an-operator-secret'
BASE_URL='http://127.0.0.1:8000'
```

`curl --fail-with-body` makes HTTP errors fail automation while preserving the
response body that explains the problem.

List audit events:

```bash
curl --fail-with-body -H "X-API-Key: $API_KEY" \
  "$BASE_URL/v1/audit-events"
```

Create a site:

```bash
curl --fail-with-body -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d @site.json \
  "$BASE_URL/v1/sites"
```

Queue a convergence, then poll it:

```bash
curl --fail-with-body -X POST -H "X-API-Key: $API_KEY" \
  "$BASE_URL/v1/deployments"
```

Save the returned `id`, then poll `GET /v1/deployments/{id}`. A successful
`202` means the work was queued, not that convergence succeeded.

Query certificate state for a site:

```bash
curl --fail-with-body -H "X-API-Key: $API_KEY" \
  "$BASE_URL/v1/sites/example-cdn/certificate"
```

## Verify API access

Check the public health route, then an authenticated route:

```bash
curl --fail-with-body "$BASE_URL/health"
curl --fail-with-body -H "X-API-Key: $API_KEY" "$BASE_URL/v1/sites"
```

The first request confirms process health. The second confirms authentication
and database access. A health response alone does not prove the key works.

## Recover from an API failure

- For `401`, verify the header and configured key without logging the secret.
- For `429`, stop the failing client and wait for the one-minute window to
  clear. Behind a proxy, all clients may share the same source address.
- For a queued deployment that later fails, inspect its deployment record and
  follow [Deployment lifecycle troubleshooting](/docs/guides/troubleshooting#deployment-lifecycle).
