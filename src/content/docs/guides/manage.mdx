# Managing edge hosts

Use this guide to add an edge host to the fleet or take one out of management
without cutting live traffic. For the responsibility split and why the
controller converges rather than serves, see [Architecture](/docs/architecture).

## Before you begin

- Confirm the edge meets the platform floor: Debian 12+ or Ubuntu 24.04+.
- Prepare a non-root SSH user with narrowly managed sudo. Root login must stay
  disabled; privilege escalation is explicit per play.
- Have the edge address and at least one trusted management CIDR for SSH.
- Run `blitzecdn doctor` and confirm no deployment or rollback is running.

<Callout type="info">
  An edge only changes when you deploy. Adding or removing an edge updates the
  inventory and desired state; the edge itself changes on the next convergence.
  See [Deploying](/docs/guides/deployment).
</Callout>

## Add an edge

```bash
blitzecdn edge add edge-01 --host 192.0.2.10 \
  --ssh-source 198.51.100.0/24 --user deploy
```

`--ssh-source` is repeatable and at least one is required; an empty list
deliberately fails closed. `--user` defaults to `deploy`.

Verify the edge is present before converging it:

```bash
blitzecdn edge list
```

<Callout type="warning">
  Bootstrap the host out of band — install the OS, create the non-root sudo
  user, and set its initial state — before adding it. The edge roles harden the
  host but do not provision the machine.
</Callout>

## Deploy to the new edge only

Prove the new host in isolation with [`--limit`](/docs/reference/cli#blitzecdn-deploy),
which resolves names and globs against the inventory and can only ever narrow
the fleet:

```bash
blitzecdn plan --limit edge-01
blitzecdn deploy --limit edge-01 --yes
```

Probe every proxied hostname externally through the new edge. Only then run a
new plan against the complete inventory and deploy so the rest of the fleet
reaches the same state. See [Production](/docs/guides/production) for the staged
rollout policy.

## Verify the edge

```bash
blitzecdn edge list --json
blitzecdn status --limit 1
```

Confirm the edge appears in the inventory, the hostname answers, and every
proxied site resolves. Edges keep serving when the controller is unavailable, so
reach the edge directly rather than through the controller.

## Remove an edge

```bash
blitzecdn edge remove edge-02 --yes
```

Removing the edge from inventory stops the next deploy from converging it; it
does not change what the host already serves. If prod traffic still points at
that host, its catch-all answers unlisted hostnames with `444` (a closed
connection), not your origin — see [Domains and records](/docs/reference/domains).

<Callout type="error">
  Never remove an edge that still receives live traffic. Either shift traffic
  off it in DNS first, or converge the remaining fleet and decommission the host
  as a separate step. Removal is about leaving management scope, not about
  decommissioning hardware.
</Callout>

## Recover from a bad add or remove

Re-add a removed edge and converge only it, verifying the fingerprint again:

```bash
blitzecdn edge add edge-02 --host 198.51.100.33 \
  --ssh-source 198.51.100.0/24 --user deploy
blitzecdn deploy
```

Rerun `blitzecdn plan` before any retry after a partial, ambiguous, or timed-out
convergence. If a host is lost, rebuild it off the controller — the edges are
not a supported database substitute for the controller — then add it back as
above. For a failed or lost host during serving, continue with
[Incident response](/docs/guides/incidents).
