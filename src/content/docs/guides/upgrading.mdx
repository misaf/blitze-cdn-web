# Upgrading

Upgrade BlitzeCDN as a versioned pair. Do not update the controller or edge
collection independently unless the [compatibility matrix](/docs/reference)
explicitly lists that combination.

## Before you begin

- Read both component release notes and identify desired-state format changes.
- Stop new site mutations and wait for the deployment lock to be free.
- Create and verify an encrypted [controller backup](/docs/guides/backup).
- Record current controller, edge collection, database, and desired-state
  versions plus the latest successful deployment ID.
- Prepare a rollback package for the currently installed controller and roles.

<Callout type="warning">
  A database or desired-state migration may not be reversible. Restoring the old
  binary without its matching database backup is not a rollback plan.
</Callout>

## Upgrade order

1. Restore the backup onto an isolated controller and test the new controller
   against that copy without production inventory.
2. Install the controller version named in the compatibility matrix.
3. Install its matching edge collection.
4. Run `blitzecdn doctor` and `blitzecdn validate` before allowing mutations.
5. Run `blitzecdn plan` with a canary inventory, review every proposed change,
   then deploy the canary.
6. Probe each canary hostname externally. Widen only after configuration,
   certificates, cache behavior, and origin traffic are correct.
7. Run a fresh plan against the complete inventory and deploy the same desired
   state to the remaining edges.

## Verify

```bash
blitzecdn doctor
blitzecdn validate
blitzecdn status --limit 3
blitzecdn audit --limit 20
```

Confirm the controller and edge versions match the compatibility matrix, no
deployment remains `queued` or `running`, and external probes succeed from more
than one network.

## Recover

If validation fails before remote work, reinstall the previous pair and restore
the matching database/configuration backup if a migration ran. If convergence
started, treat the result as partial or unknown: inspect the deployment record,
restore the controller pair if required, run `plan`, and converge a known
successful snapshot. Never delete a live deployment lock.

Escalate to the [incident runbook](/docs/guides/incidents) when serving traffic,
certificate validity, or controller truth cannot be established quickly.
