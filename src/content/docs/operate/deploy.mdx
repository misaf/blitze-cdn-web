# Deploying

Use this guide to apply desired state safely and recover from an unsuccessful
run. Interactive deployment includes validation and a check-mode preview.
For the surrounding lifecycle, return to
[Operate BlitzeCDN](/docs/operate#5-day-to-day-operation).

## Before you begin

- Back up the controller database and certificate state.
- Verify inventory, SSH fingerprints, and management CIDRs.
- Make sure no other deployment or rollback is running.

<Callout type="warning">
  A timeout does not prove that no edge changed. Always run a new plan before
  retrying a timed-out or interrupted deployment.
</Callout>

```bash
blitzecdn deploy # validate, preview, confirm, and apply
```

## Deployment checklist

<Steps>

### Protect controller state

Verify a current backup of `.state/control-plane.db` and managed certificate
state. Use the [backup procedure](/docs/operate/backup-restore#create-a-consistent-backup).

### Verify remote trust

Verify inventory addresses and SSH host fingerprints out of band. Confirm the
non-root deployment user has narrowly managed sudo access.

### Confirm firewall access

Set trusted management CIDRs. An empty
`blitzecdn_firewall_ssh_sources` list deliberately fails closed.

### Check the origins

Run `blitzecdn origin check`. It connects to every enabled site's origin the way
the edge will and catches what `validate` cannot see — an origin that does not
resolve, is not listening, or presents a certificate that does not match the SNI
the edge sends. These surface as `502`s minutes after a deploy that reported
success.

The probe runs from the control plane, not from an edge, so a pass is good
evidence rather than proof. A failure is almost always real.

### Validate, preview, and apply

Run `blitzecdn doctor`, then `blitzecdn deploy`. Review the check-mode preview
and confirm only when it matches your intended change.

### Inspect

Inspect `blitzecdn status DEPLOYMENT_ID` and probe edge health externally.

</Steps>

## Understand the deployment record

Interactive `deploy` validates local state, runs Ansible check mode, and asks
before applying. The applied deployment records an immutable snapshot,
transitions it `queued → running`, invokes Ansible, then records `succeeded`,
`failed`, or `timed_out`. If the controller restarts mid-run, startup marks
unfinished records `abandoned`—rerun `deploy` and review its preview before
retrying.

Only one deployment can hold the lock at a time. Work that can be rejected before
queuing — no rollback target, a deployment already running — fails synchronously
rather than queueing.

## Rollback

See [Deployment lifecycle](/docs/understand/deployment-model) for the rollback semantics. In
short, rollback is safe under concurrency because selection, convergence, and
state replacement occur under a single lock hold.

```bash
blitzecdn rollback            # latest successful state different from current
blitzecdn rollback --check    # preview
blitzecdn rollback DEPLOYMENT_ID
```

Applied rollback prompts interactively. Add `--yes` only after reviewing the
target when running non-interactively.

## Verify the result

```bash
blitzecdn status --limit 1
blitzecdn audit --limit 5
```

Require `status: succeeded`, then probe traffic through at least one edge in the
rollout. For staged fleets, verify each stage before widening the inventory.

## Recover from failure

Read the retained deployment output and determine whether any edge changed.
Correct the cause, run `validate`, and create a new plan. Use rollback only when
you have selected a known successful applied snapshot; rollback is another
convergence, not an undo of remote side effects outside BlitzeCDN.

## Rate and scope

For a large fleet, roll out in stages rather than all at once — a bad config
converged onto 25% of edges is recoverable; converged onto 100% is an incident.
The bundled playbook uses `serial: 25%`, which still reaches a quarter of the
fleet before anything stops.

For a smaller [canary](/docs/understand/glossary#canary), narrow the run with `--limit`:

```bash
blitzecdn deploy --limit edge-01
# prove the change on that edge, then finish the rollout
blitzecdn deploy
```

`--limit` accepts edge names or globs, comma separated. It is resolved against
the inventory, so it can only narrow the fleet — a name the inventory does not
declare as an edge is refused rather than passed to Ansible, and a typo fails
loudly instead of converging nothing and reporting success.

<Callout type="warning">
  A canary leaves the fleet in two states. The control plane records the limit
  on the deployment and excludes limited runs from automatic rollback selection,
  because rolling back to a snapshot only one edge received would converge every
  other edge onto a state it never ran. Finish the rollout or revert it; do not
  leave it split.
</Callout>

`rollback` deliberately accepts no limit. A successful applied rollback rewrites
canonical state, so a partial one would leave the control plane asserting a
state most edges have never been given.

## Detect drift

A deploy answers "make it so". `blitzecdn drift` answers "is it still so":

```bash
blitzecdn drift --json
```

It runs a check-mode convergence and reports, per edge, how many tasks would
change. Nothing on any edge is modified. It exits `6` when a reachable edge has
moved or an edge could not be reached — distinct from `5`, so a scheduled check
tells "the fleet moved" apart from "the check itself broke".

Read the result with two caveats. A task the roles skip under check mode cannot
be counted, so the report floors rather than exactly measures the difference: it
reliably tells you [drift](/docs/understand/glossary#drift) exists and undercounts rather
than invents it. An unreachable edge is reported as unreachable, not as drift —
nothing was learned about its configuration.
