# Take a real site live

By the end of this tutorial one hostname you own is served by your edges over
HTTPS, with a certificate BlitzeCDN renews for you. It continues where the
[First deployment](/docs/operate/first-deployment) stops: that tutorial ends on HTTP with a
documentation hostname, and this one replaces both halves of that.

Expect about 30 minutes of work, plus however long your DNS change takes to
propagate.

## Before you begin

- Complete [First deployment](/docs/operate/first-deployment), so a controller and at
  least one edge are already converging.
- Own a real hostname, and have access to change records in its zone — or a
  direct line to whoever does. This is the step most likely to stall.
- Have an origin server that already answers for that hostname's content.
- Have Certbot installed on the controller, and `BLITZE_ACME_DEFAULT_EMAIL` set
  or an email ready to pass per request.
- Read [How it works](/docs/understand) if the order of the steps below
  is not yet obvious.

<Callout type="warning">
  If the hostname already serves live traffic, lower its DNS TTL before you
  start — at least the current TTL's worth of time ahead — so cached copies of
  the old address expire before the cutover. See [DNS
  hand-off](/docs/operate/dns#lower-the-ttl-before-moving-a-live-hostname).
</Callout>

<Steps>

### Add the hostname and a way back to the origin

Register the zone if it is not already known, then add the hostname as a proxied
record whose value is your origin's address:

```bash
blitzecdn domain add example.com
blitzecdn record add example.com www --value 198.51.100.10 --proxied
```

Add a second, **unproxied** record so the origin stays reachable under a name of
its own. Once `www` points at an edge, it no longer reaches the origin server, and
you will still want a way in for deploys and debugging:

```bash
blitzecdn record add example.com origin --value 198.51.100.10
```

Confirm what the edges will serve, and that the origin answers the way an edge
will ask:

```bash
blitzecdn site list
blitzecdn origin check
```

`origin check` connects with the same SNI and port an edge uses. It exits `3` if
an origin does not resolve, is not listening, or presents a certificate that does
not match. Fix that before continuing — a certificate over a dead origin is a
padlock on a `502`.

### Deploy so the edges serve it over HTTP

```bash
blitzecdn deploy
```

Review the preview and confirm. This has to happen **before** requesting a
certificate: validation fetches a challenge token over port 80 from the edge, so
the virtual host must already exist there.

The hostname is now served over HTTP, but only to requests that reach an edge.
Public DNS still points elsewhere, so test by resolving it yourself:

```bash
curl --fail --silent --show-error \
  --resolve "www.example.com:80:192.0.2.10" \
  "http://www.example.com/" \
  --output /dev/null --write-out 'HTTP %{http_code}\n'
```

Substitute your hostname and one edge address. A 2xx or 3xx from your origin
means the listener, virtual host, proxy path, and origin all work together.

### Publish public DNS

Point the hostname at your edge addresses in whatever system hosts the zone.
`blitzecdn edge list` reports the addresses; `blitzecdn dns export` reports which
hostnames need publishing.

A proxied record exports no address on purpose — the edge addresses are a fact
about your fleet, not about the record. The full explanation and the rollback
order are in [Publish DNS](/docs/operate/dns).

Wait for the change to propagate, then confirm what the world now sees:

```bash
dig +short www.example.com A
```

### Check readiness, then request the certificate

To let the CLI run readiness checks, request certificates for ready proxied
sites, and perform the required installation deployment in one operation, use:

```bash
blitzecdn deploy --request-certificates
```

Sites whose public DNS is not ready are reported as skipped without contacting
the certificate authority. The explicit steps below remain useful when you want
to inspect or automate each operation separately.

```bash
blitzecdn cert preflight www-example-com
```

This is the step that turns a confusing certbot failure into a sentence. It
resolves the hostname against your edge addresses, reads `CAA`, and confirms the
virtual host is in the last successful deployment — the three things HTTP-01
depends on. It exits `3` and names what to fix if any of them is not met, and
contacts no certificate authority, so you can run it as often as you like while
DNS settles.

Once it reports the site is ready:

```bash
curl --fail-with-body -X POST \
  -H "X-API-Key: $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"email":"operator@example.com"}' \
  "$BASE_URL/v1/sites/www-example-com/certificate/request"
```

Set `API_KEY` and `BASE_URL` as shown in
[Common API workflows](/docs/operate/http-api#common-workflows). The request runs the
same checks and returns `409` without contacting the authority if one blocks, so
a rate-limited request is never spent on an attempt that would fail.

### Deploy again to install it

```bash
blitzecdn record always-use-https example.com www --on
blitzecdn deploy
```

Issuance stored the certificate on the controller. The setting enables the
port-80 `308` redirect, and the deploy applies both changes to the edges. Until
it runs, the hostname is still served over plain HTTP. Use `--off` and deploy
again if the hostname must remain available over both schemes; HTTPS stays
available. The ACME challenge path remains served over HTTP in either mode so
renewals continue to work.

</Steps>

## Verify

Confirm what the edge actually serves, not only what the controller stored:

```bash
curl --fail --silent --show-error \
  "https://www.example.com/" \
  --output /dev/null --write-out 'HTTP %{http_code}\n'

openssl s_client -connect www.example.com:443 \
  -servername www.example.com </dev/null
```

Check the subject alternative names, issuer, and expiry. Then confirm the
controller agrees and knows it can renew:

```bash
blitzecdn cert list
```

`source: acme` and `renewable: true` mean BlitzeCDN will keep it current on its
own. `uploaded` certificates are never renewed automatically.

## What now runs itself

Install the two units in the control plane's `packaging/systemd/` directory:

- **`blitzecdn-cert-renew.timer`** — twice daily. Reissues ACME certificates with
  30 days or fewer remaining, runs the same preflight checks first, deploys
  renewed material, and signals either kind of failure through its exit code.
- **`blitzecdn-drift.timer`** — hourly. Reports an edge that no longer matches
  desired state and exits `6`. It changes nothing.

Your one ongoing obligation is to keep public DNS pointed at the edges. Renewal
re-validates over HTTP-01 exactly as issuance did, so a hostname quietly moved
away will start failing renewals.

## Roll back

To take the hostname off the CDN, reverse the halves in this order so nothing is
refused mid-change:

1. Point public DNS back at the origin address and wait out the TTL.
2. Turn the proxy off and deploy:

   ```bash
   blitzecdn record proxy example.com www --off
   blitzecdn deploy
   ```

Doing it the other way round leaves DNS aimed at an edge that no longer serves the
hostname, and the catch-all answers those requests with a `444`.

To undo a bad deploy rather than retire the hostname, roll back to the previous
snapshot instead — see [Rollback](/docs/understand/deployment-model#rollback).

## Troubleshooting

- **`cert preflight` says the hostname is not an edge address** — DNS has not
  propagated, it was published in a non-authoritative zone, or an edge behind
  NAT needs an explicit `--public-address` distinct from its SSH `--host`.
- **`cert preflight` says the site is not deployed** — you skipped or lost the
  deploy in step 2. Run `blitzecdn deploy`.
- **`CAA` blocks issuance** — the zone permits other authorities but not yours.
  See [Confirm CAA permits your CA](/docs/operate/dns#confirm-caa-permits-your-ca).
- **Issuance fails despite a clean preflight** — port 80 is not reaching the
  edges, or something upstream redirects `/.well-known/acme-challenge/`. The
  controller cannot see either.
- **HTTPS works but the page is wrong** — the certificate is fine and the origin
  is the problem. Run `blitzecdn origin check`.
- Anything else: [Troubleshooting](/docs/operate/troubleshooting).
