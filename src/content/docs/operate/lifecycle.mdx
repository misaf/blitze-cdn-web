# Install, rebuild, and remove

Use this guide to put BlitzeCDN on a machine or take it off again.
For the condensed end-to-end sequence, return to
[operator runbook](/docs/operate).

## Lifecycle operations are not interchangeable

| Operation                  | Supported path                | Effect on local state                                            |
| -------------------------- | ----------------------------- | ---------------------------------------------------------------- |
| Fresh install              | `install.sh standalone`       | Creates state                                                    |
| Repair/re-provision        | Rerun `install.sh standalone` | Preserves database, credentials, certificates, and desired state |
| Fresh rebuild              | `install.sh --fresh`          | Deletes all owned state, then reinstalls the same release        |
| State-preserving uninstall | Not implemented               | Back up externally before purging                                |
| Complete purge             | `install.sh --uninstall`      | Deletes all owned controller and local-edge state                |

## Before you begin

- The [controller](/docs/understand/glossary#controller) needs **Python 3.12 or newer**,
  which means **Debian 13+ or Ubuntu 24.04+**. Debian 12 ships Python 3.11 and
  cannot run the control plane, even though it remains a supported
  [edge](/docs/understand/glossary#edge) platform. A standalone installation makes one host
  both, so it takes the higher floor.
- Provisioning a whole server needs root and Debian or Ubuntu. A controller-only
  installation needs neither.
- Certbot is required on the controller only if you plan to request ACME
  certificates. The server installer installs it for you.

## Choose an installation

|               | Standalone server                                                                               | Controller-only checkout                        |
| ------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| What it is    | One host that is both control plane **and** its own edge                                        | A machine that manages remote edges             |
| Root required | Yes                                                                                             | No                                              |
| Creates       | Service accounts, a sudo rule, systemd services, loopback SSH trust, `/usr/local/bin/blitzecdn` | `.venv`, `.state`, and `~/.local/bin/blitzecdn` |
| Install with  | `install.sh standalone`                                                                         | `./install.sh`                                  |
| Remove with   | `install.sh --uninstall`                                                                        | Deleting the checkout                           |

A standalone server is the fastest way to a working system and the right shape
for a single-node deployment. A controller-only checkout changes nothing about
the machine it runs on and is what you want when the edges live elsewhere.

## Install a standalone server

Clone the maintained `2.x` branch, then provision from it:

```bash
sudo git clone --branch 2.x https://github.com/misaf/blitze-cdn-cp.git /opt/blitzecdn
sudo /opt/blitzecdn/install.sh standalone \
  --admin-cidr 203.0.113.8/32 --email ops@example.com
```

Replace `203.0.113.8/32` with the network you administer SSH from, and
`ops@example.com` with your ACME account address. Both are required — the
installer cannot invent them. Add `--public-address` for a host behind NAT, and
`--deploy` to converge the edge immediately instead of preparing only.

<Callout type="error">
  Read `install.sh` before you run it. It runs as root: it creates a service
  account, writes a sudo rule, generates SSH keys, and enables public services.
  Clone a tag rather than a branch so you provision from the exact revision you
  read.
</Callout>

`/opt/blitzecdn` is not a preference. The installer refuses to provision from
anywhere else because the hardened systemd units use that path.

The result is a host with a `blitzecdn` command on `PATH`, the API on loopback,
an edge named `edge-local` in the inventory, and no edge configuration deployed
until you ask for it.

## Install a controller-only checkout

```bash
git clone --branch 2.x https://github.com/misaf/blitze-cdn-cp.git
cd blitze-cdn-cp
./install.sh
```

This creates no accounts, no services, and no system files. It builds `.venv`,
installs the Ansible collection dependencies, initializes local configuration,
and puts a `blitzecdn` command in `~/.local/bin` pinned to this checkout so you
can run it from any directory.

Set `BLITZECDN_DEV=1` to install the test and lint tooling as well.
`BLITZECDN_WRAPPER_DIR` puts the command somewhere else, and
`BLITZECDN_USER_WRAPPER=0` skips it — run `.venv/bin/blitzecdn` instead. See the
[First deployment](/docs/operate/first-deployment) for the complete walkthrough.

## Repair or re-provision a standalone server

Rerun the installed release with the original host policy values:

```bash
sudo /opt/blitzecdn/install.sh standalone \
  --admin-cidr 203.0.113.8/32 \
  --public-address 203.0.113.10 \
  --email ops@example.com
```

This rebuilds the locked virtual environment, installs pinned Ansible
dependencies, verifies the current schema, and reconverges the controller.
It preserves API keys, the database, desired state, edges, certificates, and
history. It does not deploy unless `--deploy` is supplied. There is no separate
standalone “reinstall software only” command; this is the supported repair.

The control-plane role rewrites `/var/lib/blitzecdn/.ssh/known_hosts` with the
standalone host's loopback keys. If this controller manages remote edges,
re-verify and record their fingerprints before running a plan or deployment.

## Complete purge

```bash
sudo /opt/blitzecdn/install.sh --uninstall
```

Add `--yes` to skip the confirmation prompt. This is the only supported
standalone uninstall and it is a complete purge; there is no mode that keeps
local BlitzeCDN state. It removes `/opt/blitzecdn` and everything in it — source,
`.venv`, database, certificates, Certbot state, SSH key, locks, logs, and
collections — plus services and units, `/etc/blitzecdn`, API keys, the CLI
wrapper, sudo rule, service accounts and expected homes, and the
Nginx sites, TLS files, cache, access log, registry, and managed drop-ins this
host converged as an edge. Run `install.sh --uninstall --help` for the exact list.

Packages the installer added, such as Certbot and nginx, are left in place: the
uninstaller cannot know whether you wanted them for something else. Nothing
outside the listed paths changes, and running it twice is safe.

<Callout type="warning">
  This irreversibly deletes desired state, inventory, deployment/workflow
  history, audit events, API keys, SSH key material, managed certificates, and
  local state. Copy a tested backup outside `/opt/blitzecdn` and
  `/etc/blitzecdn` first.
</Callout>

If an account cannot be removed — usually because a process is still running as
it — the uninstaller reports which one and exits non-zero rather than claiming
success:

```console
$ sudo /opt/blitzecdn/install.sh --uninstall --yes
error: BlitzeCDN was not fully removed:
  - deploy: the account still exists (still running: 5744 sleep)
Stop whatever still uses the account — 'loginctl terminate-user ACCOUNT',
or kill the processes listed — then run the uninstaller again.
```

The rest of the cleanup has already run, so stop the named processes and run it
again to finish.

### Remove a controller-only checkout

Do not point `--uninstall` at a developer machine: it targets `/opt/blitzecdn`
and the system accounts a server installation creates. Remove a checkout by hand
instead — it holds its own `.venv` and `.state`, and the wrapper is the only file
outside it:

```bash
rm -rf /path/to/blitze-cdn-cp
rm -f ~/.local/bin/blitzecdn
```

## Rebuild from scratch

```bash
sudo /opt/blitzecdn/install.sh --fresh \
  --admin-cidr 203.0.113.8/32 --email ops@example.com
```

Resolves and stages the exact replacement checkout before it removes the
working installation, so a missing ref or network failure leaves the current
controller untouched. It then performs the complete purge above, moves the
staged source into place, and installs it exactly as a new server. An exact
release tag remains on that tag, a `2.x` installation remains attached to that
branch, and any other development checkout remains pinned to its exact commit.
The checkout must be the upstream Git repository. The standalone options pass
through unchanged. The rebuilt system has empty state.

## Verify

After any install:

```bash
blitzecdn --version
blitzecdn doctor --json
systemctl status blitzecdn-api.service
```

`doctor` reports local readiness without contacting remote servers. On a
standalone server the API answers on loopback only; reach it over an SSH tunnel:

```bash
ssh -L 8000:127.0.0.1:8000 OPERATOR@THIS_SERVER
```

After an uninstall, confirm nothing survived:

```bash
test ! -e /opt/blitzecdn
test ! -e /etc/blitzecdn
! getent passwd blitzecdn
! getent passwd deploy
systemctl list-unit-files 'blitzecdn-*'
```

## Troubleshooting

- An installer that stops at `requires Python 3.12 or newer` means the
  distribution's interpreter is too old — Debian 12 is the usual case. See
  [Before you begin](#before-you-begin).
- `refusing unexpected origin URL` means the checkout's `origin` is not the
  upstream repository. `--fresh` fetches code and runs it as root, so it accepts
  only that remote.
- `clone or copy this release to /opt/blitzecdn` means `standalone` was run from
  another directory. Move the checkout and run it again.
- For symptoms after a deployment rather than an installation, see
  [Troubleshooting](/docs/operate/troubleshooting).
