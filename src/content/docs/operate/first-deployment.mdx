# First deployment

By the end of this tutorial, one site will be deployed across your edge servers.
Expect about 15 minutes when SSH and package access are ready. Run every command
from the release checkout created below. Editable development installation
belongs in the control-plane repository's README.

<Callout type="warning">
  This is a first-deployment lab, not a production runbook. It deliberately
  starts with HTTP only and uses a documentation hostname. Work through the
  [production checklist](/docs/operate/production) before serving real traffic.
</Callout>

For the order these steps follow and why, see
[How it works](/docs/understand).

## Before you begin

- One controller with Python 3.12 or newer — Debian 13+ or Ubuntu 24.04+.
- Certbot on the controller if you plan to request ACME certificates.
- Debian 12+ or Ubuntu 24.04+ edge servers, each with a non-root SSH user that
  has narrowly scoped sudo.
- Your own inventory of addresses and **SSH host fingerprints, verified out of
  band**.

<Steps>

### Install the control plane

```bash
git clone --depth 1 https://github.com/misaf/blitze-cdn-cp.git
cd blitze-cdn-cp
./install.sh
```

<Callout type="info">
  To provision a whole server — control plane and edge on one host — in a single
  command instead, see [Installing &
  removing](/docs/operate/lifecycle#install-a-standalone-server). Read the
  script before you run it: it runs as root and provisions the host.
</Callout>

This checks out the latest version from the repository's default branch. Verify
the repository owner before production use. The installer verifies Python,
creates `.venv`, installs the Ansible collections the roles depend on, and
initializes local configuration. For repeatable production deployments, check
out a tested release tag instead of the default branch — the Ansible roles ship
with the control plane, so a release pins its own edge automation.

The installer also puts a `blitzecdn` command in `~/.local/bin`, so you can run
the control plane from any directory. It pins this checkout as the project
directory, which is what keeps your state, database, and certificates in one
place no matter where you run it from. The commands below use
`.venv/bin/blitzecdn` so they work before you add `~/.local/bin` to your `PATH`;
once it is there, run `blitzecdn` instead.

Set `BLITZECDN_WRAPPER_DIR` to install that command somewhere else, or
`BLITZECDN_USER_WRAPPER=0` to skip it. Installing from a second checkout
repoints the command at the newer one.

### Register your first edge

```bash
.venv/bin/blitzecdn edge add edge-01 \
  --host 192.0.2.10 \
  --user deploy \
  --ssh-source 198.51.100.0/24
```

This records the edge in the inventory and the management network allowed to
reach its SSH port. Replace the documentation addresses with your real edge and
trusted network. At least one `--ssh-source` is required so the firewall cannot
accidentally lock out every administrator.

Nothing on the edge changes yet — it changes when you deploy, at the end of this
tutorial. The installer has already created private local configuration and an
empty inventory without overwriting existing files, and the CLI reads `.env`
automatically.

### Install your login key on the edge

BlitzeCDN accepts no way in but a key — the controller connects with
`PreferredAuthentications=publickey` and `PasswordAuthentication=no`, and the
first deploy makes the edge itself reject everything but keys.

Create a key if you do not already have one, and install the **public** half on
the edge under the account you passed to `--user`:

<Callout type="error">
  The controller keeps `host_key_checking = True` and BlitzeCDN never disables
  it. Before you connect, verify each edge's host-key fingerprint through a
  trusted channel and add it to `known_hosts`. See [SSH host
  keys](/docs/understand/security). A connection that prompts you to accept an
  unknown key is a connection you cannot yet trust.
</Callout>

For a standalone service account, use the exact fingerprint and `known_hosts`
procedure in [Prepare SSH identity and trust](/docs/operate/edges#prepare-ssh-identity-and-trust).

```bash
EDGE_HOST=edge-01.example.net
ssh-keygen -t ed25519 -C "blitzecdn-operator"
ssh-copy-id -i ~/.ssh/id_ed25519.pub deploy@"$EDGE_HOST"
```

Most cloud images inject an operator key at provisioning time, in which case
`ssh-copy-id` is unnecessary — it also needs password login, which a
pre-hardened image will already refuse. Either route is fine; what matters is
that the account can log in with a key before you deploy.

Confirm it, and confirm that no password was involved:

```bash
ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no \
  deploy@"$EDGE_HOST" true
```

<Callout type="warning">
  Run this for every account you list in `blitzecdn_sshd_allow_users`, or for
  the `--user` account if you leave that list empty. The `blitzecdn_sshd` role
  checks each one for a non-empty `authorized_keys` and **fails the deploy**
  rather than disabling passwords on a host where that would strand you. A
  failure here means the key is missing, not that the tooling is broken.
</Callout>

If your key has a passphrase, load it into an agent before deploying. The
controller runs SSH with `BatchMode=yes`, so an unloaded passphrase fails the
deploy immediately instead of hanging on a prompt:

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
```

### Prove readiness, then deploy

```bash
.venv/bin/blitzecdn doctor --json
.venv/bin/blitzecdn domain add example.com
.venv/bin/blitzecdn record add example.com cdn \
  --value 198.51.100.20 \
  --proxied
.venv/bin/blitzecdn deploy
```

- `doctor` reports local readiness without contacting remote servers.
- `domain add` registers the zone.
- `record add --proxied` points `cdn.example.com` at the origin
  `198.51.100.20` and routes it through the edge. Without `--proxied` the record
  bypasses the CDN and the edge serves nothing for it. See
  [Domains and records](/docs/understand/reference/records).
- `deploy` validates the configuration, previews the Ansible changes, and asks
  you to confirm before applying them. Use `--yes` only in reviewed automation
  where validation and preview happen separately.

The timestamps, paths, and deployment IDs vary. Look for these stable fields:

```console
$ .venv/bin/blitzecdn doctor --json
{
  "api_auth_configured": true,
  "configuration_errors": [],
  "python_supported": true,
  "state_dir": "..."
}
```

```console
$ .venv/bin/blitzecdn deploy
Configuration is valid. Previewing changes...
...
Apply these changes to all configured edges? [y/N]: y
status: succeeded
check_mode: false
...
```

</Steps>

## Verify the deployment

Inspect the latest deployment and the operator audit trail:

```bash
.venv/bin/blitzecdn status --limit 1
.venv/bin/blitzecdn audit --limit 5
```

The latest records should contain these fields (IDs and timestamps vary):

```console
$ .venv/bin/blitzecdn status --limit 1
- status: succeeded
  check_mode: false
  return_code: 0
  ...

$ .venv/bin/blitzecdn audit --limit 5
- operator: cli
  action: deployment.succeeded
  resource_type: deployment
  ...
```

Now exercise the real HTTP path without waiting for public DNS. Substitute the
hostname passed to `--domain` and one edge IP:

```bash
SITE_HOST=cdn.your-domain.example
EDGE_IP=192.0.2.10
curl --fail --silent --show-error \
  --resolve "$SITE_HOST:80:$EDGE_IP" \
  "http://$SITE_HOST/" \
  --output /dev/null \
  --write-out 'HTTP %{http_code}\n'
```

A healthy origin normally returns a success such as `HTTP 200`; the exact 2xx
or 3xx code depends on your origin. `--fail` makes 4xx/5xx responses fail the
command. BlitzeCDN records convergence, but only this external request proves
the listener, virtual host, proxy path, and origin response together.

## Clean up the lab site

If this was only an evaluation, remove its desired state and converge that
removal on the edges. Removing the zone removes its records with it:

```bash
.venv/bin/blitzecdn domain remove example.com
BLITZE_ALLOW_EMPTY_SITES=true .venv/bin/blitzecdn deploy
```

Both destructive commands prompt for confirmation, and deploy shows its preview
before applying. `BLITZE_ALLOW_EMPTY_SITES=true` is required because this
tutorial removes the final managed site; review the empty plan carefully. It
affects only this invocation. Removing desired state does not delete unrelated
origin data or records at your external DNS provider.

## Recover from a failed first deployment

Do not immediately retry a failed or timed-out run. Read its retained output,
correct the inventory or desired state, then run `deploy` and review its preview.
See [Deployment lifecycle troubleshooting](/docs/operate/troubleshooting#deployment-lifecycle)
for timeout and partial-state guidance.
