# Deployment lifecycle

This page explains site desired state, deployment snapshots, and rollback
selection. The ordered operational checklist lives in
[Deploy and roll back](/docs/operate/deploy#deployment-checklist).

## Operational boundary

Deployment and rollback serialize changes to canonical state. Operators protect
that boundary by identifying the site owner and intended state, retaining a
current backup, and avoiding competing deployment work.

## What a site is

A site is the validated, provider-independent desired state for one CDN virtual
host. It is governed by the `CdnSite` model, and every value that may enter an
Nginx template is constrained at the domain boundary — names, DNS/IP syntax,
ports, durations, and absolute certificate paths.

<Callout type="info">
  You do not create sites. A site is **derived** from a proxied DNS record:
  proxy a record and its site appears, unproxy it and the site is gone. The
  fields below are set on the record. See [Domains and
  records](/docs/reference/records).
</Callout>

The core fields:

| Field                                           | Meaning                                                                           |
| ----------------------------------------------- | --------------------------------------------------------------------------------- |
| `name`                                          | Unique identifier for the site.                                                   |
| `server_names`                                  | The hostnames Nginx will serve.                                                   |
| `origin_host` / `origin_port`                   | Where requests are proxied.                                                       |
| `origin_scheme`                                 | `http` or `https`.                                                                |
| `origin_request_host` / `origin_sni`            | The `Host` header / SNI Nginx sends to the origin. SNI defaults to `origin_host`. |
| `cache_enabled`                                 | Whether responses are cached.                                                     |
| `cache_valid_success` / `cache_valid_not_found` | Cache durations for success and not-found responses.                              |
| `certificate_mode`                              | `disabled`, `existing`, `uploaded`, or `requested`.                               |
| `certificate_path` / `certificate_key_path`     | Paths for `existing` certificates.                                                |
| `firewall`                                      | Per-hostname request filtering at the edge.                                       |

See [HTTP API](/docs/reference/http-api) for the full model, or
[Ansible roles](/docs/reference/ansible) for how they map onto the edge role.

## Desired state vs. what runs

The controller keeps a **desired state** — what you want — and deploys it to
every edge. The control plane and roles ship together, and contract tests check
the rendered site keys against the role argument specification.

Site mutations are validated and committed transactionally to SQLite before
anything touches a host. They produce an audit record and do not reach the
network by themselves.

## Snapshots

Every deployment records an **immutable snapshot** of the state it applies.
Because the snapshot is immutable, checking what a given deployment did — or
returning to it later — is exact, and cannot be affected by later edits.

## Rollback

Rollback selects an explicit previously successful applied snapshot (or the
latest successful state that differs from the current one), converges it, and
only after success replaces canonical desired state in a single database
transaction. Selection, convergence, and that replacement all happen under one
hold of the deployment lock, so a concurrent site edit cannot be silently
discarded.

The CLI can select the latest different successful snapshot or an explicit
deployment ID, and it can preview either choice. Applied rollback requires
confirmation. See the [`rollback` reference](/docs/reference/cli#blitzecdn-rollback)
for the exact forms.

## The lock

A deployment acquires an OS-level lock on an open file for the whole run. The
worker releases it on the way out — a timed-out run still releases it, because it
is a filesystem lock tied to the process. A controller restart marks unfinished
records `abandoned` and your next plan reflects that. See
[Deploy and roll back](/docs/operate/deploy) for the practical implications.

## Evidence of site state

The site list exposes hostnames, origin, cache policy, and certificate mode.
Validation checks the complete desired state and Ansible syntax without
changing an edge. The commands and exit behavior are defined by
[`site list`](/docs/reference/cli#blitzecdn-site-list) and
[`validate`](/docs/reference/cli#blitzecdn-validate).

## Incorrect site state

An incorrect change is recovered either by applying corrected desired state or
by selecting a known successful snapshot. Confirmation, preview, and failure
behavior belong to the [rollback procedure](/docs/operate/deploy#rollback).
