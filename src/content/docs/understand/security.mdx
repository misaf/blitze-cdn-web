# Security boundaries

BlitzeCDN validates both sides of the deployment contract, but ownership of
identity, network policy, host trust, and secret handling remains outside that
contract.

## Operator-owned controls

Controller access, edge sudo, DNS, secret rotation, backups, and break-glass
access all require an operator-owned policy. BlitzeCDN consumes those decisions;
it cannot determine the right owners, trusted management networks, or verified
SSH fingerprints.

## Trust boundaries

- **SSH host keys are operator-verified.** Verify every fingerprint through a
  trusted channel, add it to `known_hosts`, and never disable host-key checking.
- **SSH is public-key only, in both directions.** The controller dials out with
  `PreferredAuthentications=publickey`, `PasswordAuthentication=no`, and
  `BatchMode=yes`, so a deploy fails rather than falling back to a password or
  hanging on a prompt; `blitzecdn_sshd` enforces the matching policy on every
  edge. Use an SSH agent for key passphrases.
- **API keys authenticate, they do not authorize.** Keys identify an operator;
  there are no per-operator roles in this release.
- **Secrets never ride the CLI.** Keys and passwords live in environment / secret
  manager, Ansible Vault, or restrictive controller state, and are never accepted
  as CLI arguments.
- **Remote privilege escalation is explicit per play.** Global root login is
  disabled; the non-root deployment user has narrowly scoped sudo.

## Hardening the edges

The edge roles install a fail-closed baseline (see [Ansible roles](/docs/reference/ansible)):

- **Firewall (UFW)** — `blitzecdn_firewall`, enabled by default, opening only
  `80`, `443`, and SSH, and only from `blitzecdn_firewall_ssh_sources`. An empty
  source list deliberately fails closed.
- **SSH policy** — `blitzecdn_sshd`, enabled by default, accepting public keys
  and nothing else (`AuthenticationMethods publickey`, root login off). It
  refuses to run unless the account it would leave behind already has a working
  key, reloads rather than restarts the daemon, and verifies the result with
  `sshd -T` instead of trusting that the file was written.
- **Fail2Ban** — `blitzecdn_fail2ban`, protecting SSH with bounded retry,
  find-time, and ban-time defaults.
- **Kernel** — `blitzecdn_kernel`, conservative settings including TCP SYN
  cookies and keepalive tuning.

<Callout type="warning">
  Do not disable the firewall or open SSH to `0.0.0.0/0`. Confirm that your
  current management address is allowed before applying firewall changes, or you
  can lock yourself out.
</Callout>

## Protecting the control plane

- Keep `.state/` (state, certificates, locks) with mode-0600 secrets and off any
  release artifact.
- Put only your management CIDRs in the allowed list; an empty list fails.
- Run the API behind TLS and a reverse proxy that restricts source networks,
  limits request size and rate, validates trusted forwarding headers, and
  redacts authentication values from centralized logs. The application—not the
  proxy—enforces `BLITZE_API_KEYS`.
- Beware `429` throttling: behind a proxy all clients share one source address,
  so a noisy tenant can throttle everyone.

## Certificates as a privilege boundary

Certificate paths control what gets written to edges as root. They are confined
to `/etc/blitzecdn/tls/`, `/etc/ssl/`, and `/etc/letsencrypt/` by the domain
models — and re-checked by the Nginx role — so a hand-edited desired-state file
cannot point a deploy at arbitrary paths. Never relax this.

## What the operator still owns

`known_hosts` verification, the sudo policy, secret rotation, and edge network
segmentation. The tooling makes the safe path easy, but cannot verify your
out-of-band trust decisions for you.

## Operational ownership

Verification and recovery are operational procedures, not properties the
architecture can prove. Use [Verify security controls](/docs/operate/security)
before production traffic. A disclosed API key follows
[Rotate API keys](/docs/operate/api-key-rotation); uncertain identity,
controller compromise, or firewall state follows
[Respond to incidents](/docs/operate/incident-response).
