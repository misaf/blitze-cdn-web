# Understand BlitzeCDN

Start here to understand the system's invariant: changing controller state and
changing edge servers are separate operations. The pages below then follow each
boundary into implementation and exact reference.

## Every change has two halves

Nothing you type reaches a server directly. A command changes
[desired state](/docs/understand/glossary#desired-state) on the controller — validated,
committed to SQLite, and recorded in the audit trail. A separate, explicit
`deploy` makes the edges match it.

```bash
blitzecdn record add example.com www --value 198.51.100.10 --proxied
blitzecdn deploy
```

The first line changes what _should_ be true. The second makes it true. If you
run only the first, nothing on any edge has changed — and that is the single most
common source of confusion when starting out.

<Callout type="info">
  The same split applies to certificates. Issuing one stores it on the
  controller; the edges keep serving the old certificate until you deploy again.
</Callout>

## The five steps to a working hostname

| #   | Step                                | What it establishes                                            | Where                                                     |
| --- | ----------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------- |
| 1   | Add a zone and a proxied record     | Which hostname the edges serve, and the origin they fetch from | [Domains and records](/docs/understand/reference/records) |
| 2   | Deploy                              | Edges now serve that hostname over HTTP                        | [Deploying](/docs/operate/deploy)                         |
| 3   | Publish public DNS at your DNS host | Visitors and certificate authorities reach an edge             | [DNS hand-off](/docs/operate/dns)                         |
| 4   | Request a certificate               | TLS, validated over HTTP-01 through those same edges           | [Certificates](/docs/operate/certificates)                |
| 5   | Deploy again                        | Edges install and serve the certificate                        | [Deploying](/docs/operate/deploy)                         |

The order is not a preference. Step 4 needs steps 2 and 3 to have happened: the
certificate authority resolves the hostname in public DNS and fetches a challenge
token over port 80 from the edge, so the virtual host has to exist and DNS has to
point at it before a certificate can be issued.

[Take a real site live](/docs/operate/go-live) walks all five in one pass.

## Records are intent, not answers

BlitzeCDN stores DNS records but does not answer DNS queries. A record tells the
edges which hostname to serve and where to fetch from; publishing the address
visitors resolve is step 3, and it happens wherever your zone is hosted.

`proxied` is the switch between the two meanings:

- **Proxied** — the edge serves this hostname, and the record's value is the
  origin it fetches from. Public DNS must answer with an edge address.
- **Unproxied** — the edge does not know the hostname exists. The record's value
  is simply what DNS should answer with; it bypasses the CDN entirely.

## What BlitzeCDN deliberately does not do

Knowing the edges of the tool saves more time than any feature list:

- **It does not host DNS.** Use `blitzecdn dns export` to hand records to
  whatever system does.
- **It does not issue wildcard certificates.** HTTP-01 cannot. Each hostname
  gets its own certificate; a wildcard has to be obtained elsewhere and
  uploaded. See
  [certificate scope](/docs/operate/certificates#scope-one-certificate-per-hostname).
- **It does not converge on a schedule.** Edges change when you deploy. A
  scheduled `drift` check reports when one has moved, but changes nothing.
- **It does not manage your origin.** The origin is yours; the edges only proxy
  to it.

## Where state lives

| State                                                          | Owner                                                  | Lost if you lose it |
| -------------------------------------------------------------- | ------------------------------------------------------ | ------------------- |
| Zones, records, derived sites, deployment history, audit trail | Controller SQLite in `.state/`                         | Yes — back it up    |
| Certificates and ACME account                                  | Controller `.state/certificates`, `.state/letsencrypt` | Yes — back it up    |
| Nginx config, TLS files, firewall rules on the edges           | Rebuilt from desired state on every deploy             | No — redeploy       |

Because the edges are rebuilt from desired state, the controller is the thing to
protect. See [Backup & recovery](/docs/operate/backup-restore).
