# HTTP API

This page documents authentication, request behavior, worked examples, and
every route. Request and response object fields are listed separately in
[HTTP API models](/docs/reference/http-api-models).

Verified against the OpenAPI schema of `BlitzeCDN control plane`.

Every route below except `GET /health` requires the `X-API-Key` header.
Ten failed authentications from one client address within a minute return
`429`. Deployment and rollback routes return `202 Accepted` with a queued
record; poll `GET /v2/deployments/{deployment_id}` for the outcome.

The key is described in the schema as the security scheme `ApiKeyAuth`
(`type: apiKey`, `in: header`, `name: x-api-key`), which every protected
operation references. It is therefore absent from the parameter tables below:
a generated client, Swagger UI's _Authorize_ button, and an imported Postman
collection all treat it as a credential configured once rather than a header
to attach per request. Handwritten requests still send the same header, as the
examples on this page do.

## Request and retry rules

- Send `X-API-Key` on every `/v2/*` request. A missing or invalid key returns
  `401`; repeated failures can return `429` for the source address.
- Read-only `GET` requests are safe to retry with bounded backoff.
- Do not blindly retry `POST` mutations. A timeout can occur after the server
  committed a record mutation or queued a deployment. Query records, deployments,
  and audit events before deciding what to do next.
- `202` means queued, not converged. Poll the returned deployment ID until it is
  terminal and inspect retained output on any non-success status.
- The API has no client-supplied idempotency key.

Common error bodies use FastAPI validation details for `422`. Authentication,
conflict, and missing-resource responses contain a short `detail` string:

```json
{ "detail": "invalid API key" }
```

Never log the request header when capturing an error response.

The status code says whether retrying can help, so branch on it rather than on
the `detail` text:

| Status | Meaning                                                                               | Retry?                                                          |
| ------ | ------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `400`  | The request, or the controller's own configuration, is wrong                          | No — a person has to change something                           |
| `404`  | No such resource                                                                      | No                                                              |
| `409`  | Conflicts with current state                                                          | Only if the state changes; a `Retry-After` header means it will |
| `422`  | The request did not validate                                                          | No                                                              |
| `502`  | Something the controller drives — Ansible, certbot, an edge — did not answer usefully | Yes, with backoff                                               |
| `503`  | The controller cannot serve this right now                                            | Yes, with backoff                                               |

`409` with `Retry-After` is the deployment lock: another deployment, rollback,
upload, or issuance holds it, and it will be free again. Every other `409` needs
the request or the state changed first.

## Worked examples

Five requests covering the shapes the rest of the page describes in the
abstract. Every payload below is validated against the models the control plane
actually serves, so they can be copied and adapted rather than guessed at.

Responses are trimmed to the fields worth seeing; the model sections list the
rest.

### Publish a hostname

A record is the unit of configuration. Adding it with `proxied` set is what
derives an edge site — there is no separate site to create. On a proxied record
`value` is the origin the edge fetches from, not the address DNS should answer
with; see [Domains, records, and sites](/docs/reference/records).

{/* schema: DnsRecord */}

```bash
curl -sS -X POST https://controller.example.com/v2/domains/example.com/records \
  -H "X-API-Key: $BLITZE_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "domain": "example.com",
    "name": "www",
    "value": "198.51.100.20",
    "proxied": true,
    "ssl_mode": "off",
    "always_use_https": false,
    "origin_request_host": "origin.internal.example.com",
    "cache_valid_success": "10m"
  }'
```

{/* schema: DnsRecord */}

```json
{
  "domain": "example.com",
  "name": "www",
  "type": "A",
  "value": "198.51.100.20",
  "ttl": 300,
  "proxied": true,
  "ssl_mode": "off",
  "ssl_automatic_mode": "auto",
  "minimum_tls_version": "1.2",
  "always_use_https": false,
  "origin_request_host": "origin.internal.example.com",
  "enabled": true,
  "certificate_mode": "disabled",
  "cache_enabled": true,
  "cache_query_string_mode": "include",
  "cache_valid_success": "10m",
  "cache_valid_not_found": "1m"
}
```

Nothing has reached an edge yet. The record is desired state until a deployment
converges it.

### Poll it to a terminal state

Poll [`GET /v2/deployments/{deployment_id}`](#get-v1deploymentsdeployment_id)
until `status` leaves `queued` and `running`. `result.hosts` is the per-edge
breakdown, and `changed` on a non-check run counts tasks that acted.

```bash
curl -sS https://controller.example.com/v2/deployments/7c1e4b90a2df46538ba0c7e15d93f8a2 \
  -H "X-API-Key: $BLITZE_API_KEY"
```

{/* schema: Deployment */}

```json
{
  "id": "7c1e4b90a2df46538ba0c7e15d93f8a2",
  "status": "succeeded",
  "operator": "ops",
  "check_mode": false,
  "created_at": "2026-03-04T09:12:44.318271Z",
  "started_at": "2026-03-04T09:12:44.902118Z",
  "finished_at": "2026-03-04T09:14:07.551903Z",
  "result": {
    "id": "7c1e4b90a2df46538ba0c7e15d93f8a2",
    "playbook": "edge.yml",
    "status": "succeeded",
    "return_code": 0,
    "started_at": "2026-03-04T09:12:44.902118Z",
    "finished_at": "2026-03-04T09:14:07.551903Z",
    "hosts": [
      {
        "host": "edge-fra-1",
        "ok": 42,
        "changed": 3,
        "failed": 0,
        "unreachable": 0,
        "changes": [
          {
            "task": "nginx : write site configuration",
            "outcome": "changed"
          }
        ]
      }
    ]
  }
}
```

A `succeeded` deployment with `changed: 0` on every host means the fleet already
matched. That is the same signal [`POST /v2/drift`](#post-v1drift) produces,
without converging anything.

### Purge one path

Purges are partial by design: each entry names a host and a URI.

{/* schema: PurgeRequest */}

```bash
curl -sS -X POST https://controller.example.com/v2/cache/purge \
  -H "X-API-Key: $BLITZE_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "entries": [
      { "host": "www.example.com", "uri": "/assets/app.css", "scheme": "https" }
    ]
  }'
```

{/* schema: PurgeResult */}

```json
{
  "purged_at": "2026-03-04T09:20:11.004512Z",
  "entries": [
    { "host": "www.example.com", "uri": "/assets/app.css", "scheme": "https" }
  ],
  "purge_all": false,
  "complete": true,
  "failed_hosts": []
}
```

`complete` is the field to branch on. A partial purge returns `409` carrying
this same body with `complete` false and the unreachable edges in
`failed_hosts` — not an error object.

### Read certificate state

```bash
curl -sS https://controller.example.com/v2/sites/www.example.com/certificate \
  -H "X-API-Key: $BLITZE_API_KEY"
```

{/* schema: CertificateStatus */}

```json
{
  "site": "www.example.com",
  "source": "acme",
  "domains": ["www.example.com"],
  "not_after": "2026-06-02T09:14:00Z",
  "days_remaining": 90,
  "expired": false,
  "renewable": true,
  "fingerprint_sha256": "9f2c4e1a7b0d3856c9e4f01b2d7a58c36e91048fbd25a7c3019e6b4d8a52f7c1"
}
```

`renewable` is a property of the certificate's source, not of how soon it
expires: an uploaded certificate is never renewable by the controller.

## `POST /v2/domains/{domain}/records`

Create Record. The body's `domain` must match the path segment.

**Request body** (required): `application/json` → [`DnsRecord`](/docs/reference/http-api-models#dnsrecord)

The certificate fields are optional. If omitted, `certificate_mode` defaults to
`disabled`, while `certificate_path` and `certificate_key_path` default to
`null`:

| Field                  | Required | Type                                                                 |
| ---------------------- | -------- | -------------------------------------------------------------------- |
| `certificate_mode`     | `false`  | `disabled` \| `existing` \| `uploaded` \| `requested`               |
| `certificate_path`     | `false`  | `string` \| `null`                                                    |
| `certificate_key_path` | `false`  | `string` \| `null`                                                    |

Send the two path fields only with `certificate_mode: existing`; otherwise,
omit them.

For automatic ACME issuance, create the record with `proxied: true` and leave
`certificate_mode` at its `disabled` default. The background certificate
reconciler periodically checks the derived site and, after deployment and
public DNS are ready, requests a certificate, changes the mode to `requested`,
and deploys the certificate. It never contacts the CA while preflight is
blocked. Configure `BLITZE_ACME_DEFAULT_EMAIL` for unattended issuance; the
default reconciliation interval is 600 seconds.

**Responses**

| Status | Description                                      | Body                  |
| ------ | ------------------------------------------------ | --------------------- |
| `201`  | Successful Response                              | [`DnsRecord`](/docs/reference/http-api-models#dnsrecord)           |

| `409`  | Record exists, or its derived site name collides | —                     |

## `POST /v2/cache/purge`

Remove cached responses from the edges. Answers inline rather than queueing: a
purge is usually made under time pressure and the caller needs to know whether
every edge actually dropped the object.

Send either `entries` or `purge_all`, never both — emptying the cache and
removing named entries are different operations, and combining them hides which
one ran. Sending neither is a `409` rather than a successful purge of nothing.

Every variant of a URL is removed: nginx keys entries by request method and by
normalized content encoding, so one URL is several entries.


**Request body** (required): `application/json` → [`PurgeRequest`](/docs/reference/http-api-models#purgerequest)

**Responses**

| Status | Description                                 | Body                  |
| ------ | ------------------------------------------- | --------------------- |
| `200`  | Purged on every edge in scope               | [`PurgeResult`](/docs/reference/http-api-models#purgeresult)         |
| `404`  | No enabled site serves a requested hostname | `object`              |
| `409`  | Nothing to purge or a contradictory request | `object`              |
| `409`  | Purged on some edges but not all            | [`PurgeResult`](/docs/reference/http-api-models#purgeresult)         |
| `422`  | Validation Error                            | [`HTTPValidationError`](/docs/reference/http-api-models#httpvalidationerror) |

A partial purge is a `409`, not a `200`. Some edges dropped the object and
others did not, so which response a client gets depends on which edge answers —
that must not read as success.

The partial `409` carries a full [`PurgeResult`](/docs/reference/http-api-models#purgeresult), not an error object. Branch on
`complete`, and retry the edges named in `failed_hosts`; `hosts` holds what each
edge reported. A request refused before it reached the fleet — nothing to purge,
or `entries` and `purge_all` together — is the other `409` and carries an
`object` with `detail`, because no purge was attempted and there is no result to
report.

## `POST /v2/certificates/renew`

Reissue ACME certificates close to expiry. Answers inline rather than queueing:
renewal changes no edge configuration, so there is nothing to converge and
nothing to poll. Returns `renewed`, `skipped`, and `failed` name lists.

Uploaded certificates are never renewed — they appear under `skipped`. Renewed
certificates reach the edges on the next deploy.

A sweep is bounded by `BLITZE_CERTIFICATE_RENEWAL_BUDGET_SECONDS` and runs on a
pool of its own, so a slow CA cannot hold a request worker indefinitely or stall
unrelated endpoints. The budget is checked between sites and never during one,
so a truncated sweep never abandons an issuance in flight. Sites it did not
reach appear under `skipped` naming the budget, and are picked up by the next
run — the same way a transient failure already is. Raise the budget, or narrow
the run with `sites`, if a sweep is regularly truncated.

The optional `sites` field narrows the run, for retrying one failure without
sending every other subscription back to a rate-limited CA. A name with no
managed certificate behind it answers `404` rather than an empty success, so an
automated caller cannot read a typo as "nothing was due". An empty list is a
`422`: it would otherwise mean "renew nothing" while reading as a filter.


**Request body** (required): `application/json` → [`RenewRequest`](/docs/reference/http-api-models#renewrequest)

**Responses**

| Status | Description                                 | Body                  |
| ------ | ------------------------------------------- | --------------------- |
| `200`  | Successful Response                         | [`RenewalResult`](/docs/reference/http-api-models#renewalresult) |
| `404`  | No managed certificate for a requested site | `object`              |
| `422`  | Validation Error                            | [`HTTPValidationError`](/docs/reference/http-api-models#httpvalidationerror) |

## `POST /v2/certificates/reconcile`

Issue first certificates for every proxied site that is ready for one, then
deploy once to install them. The same operation the scheduler runs on
`BLITZE_CERTIFICATE_RECONCILE_INTERVAL_SECONDS`, exposed so it can also be asked
for after fixing whatever was blocking preflight.

Eligibility is re-checked under the deployment lock, so this is safe to call
while the scheduler is running: only one of them can still see a site as
unissued and contact the CA. A site whose preflight blocks appears under
`skipped` and never reaches the CA; one whose issuance failed appears under
`failed` and does not stop the others.

`deployment` is `null` when nothing was issued — reconciliation converges the
fleet only when it has something new to install.


**Responses**

| Status | Description         | Body            |
| ------ | ------------------- | --------------- |
| `200`  | Successful Response | [`ReconciliationResult`](/docs/reference/http-api-models#reconciliationresult) |

## `POST /v2/ssl/automatic/reconcile`

Probe eligible records from every edge and apply upgrade-only Automatic
SSL/TLS recommendations. Records in Custom mode are never changed. A scan may
upgrade `ssl_mode` when every edge supports the stronger transport and sees
equivalent origin content; it never downgrades a record.

When one or more records change, the endpoint deploys the resulting desired
state once. Missing edges, TLS failures, origin 5xx responses, or mismatched
HTTP/HTTPS content leave the record unchanged and explain the decision in
`skipped`.

**Responses**

## `PATCH /v2/edges/{name}`

Update Edge. Each field replaces its own value; unset fields are untouched.
`public_addresses` and `ssh_sources` replace their whole list, so sending `[]`
clears them — merging would make "remove the last entry" inexpressible.

The name is not patchable. Certificates, audit history and deployment host
limits all refer to it, so a rename would orphan them; [`EdgePatch`](/docs/reference/http-api-models#edgepatch) has no such
field and forbids extras, which makes it a `422` rather than a silently ignored
key. Remove the edge and add it again under the new name.

**Request body** (required): `application/json` → [`EdgePatch`](/docs/reference/http-api-models#edgepatch)

**Responses**

| Status | Description         | Body                  |

| `404`  | Edge does not exist | —                     |
| `422`  | Validation Error    | [`HTTPValidationError`](/docs/reference/http-api-models#httpvalidationerror) |

## `DELETE /v2/edges/{name}`

Remove Edge. Tears the host down, then deregisters it — in that order. The
inventory is derived from these rows, so deregistering first would leave a host
no playbook can address again, still serving its last converged virtual hosts
and still holding their private keys.

Answers inline rather than queueing, like the purge and stats routes: one
playbook against one host. It is still bounded by `deployment_timeout_seconds`,
so set a client timeout to match.

Returns `200` with a body rather than `204`. A forced removal that tore nothing
down is a success by the caller's own instruction, and `hosts` is the only place
that distinction survives.

**Query parameters**

| Name           | Type      | Default | Description                                                                                                                                                          |
| -------------- | --------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `decommission` | `boolean` | `true`  | Strip BlitzeCDN configuration and TLS private keys from the host before deregistering it.                                                                            |
| `force`        | `boolean` | `false` | Deregister even if the teardown failed. For a host that no longer exists; on one that is merely unreachable this leaves its configuration and private keys in place. |

**Responses**

| Status | Description                                                        | Body                  |
| ------ | ------------------------------------------------------------------ | --------------------- |
| `200`  | Successful Response                                                | [`EdgeRemoval`](/docs/reference/http-api-models#edgeremoval)         |
| `404`  | Edge does not exist                                                | —                     |
| `502`  | Teardown failed and the edge was kept; retry, or pass `force=true` | —                     |
| `422`  | Validation Error                                                   | [`HTTPValidationError`](/docs/reference/http-api-models#httpvalidationerror) |

## `POST /v2/origins/check`

Ask the edges to connect to the origins they proxy to: resolve, connect, and for
an HTTPS origin complete a verified TLS handshake with the same SNI the edge
sends. Each edge answers for itself, so the response is per edge and per site.

A `POST` despite changing nothing, following `POST /v2/cache/stats`: it runs a
playbook across the fleet, which is neither cacheable nor safe to retry blindly
the way `GET` promises. Answers inline, bounded by
`BLITZE_DEPLOYMENT_TIMEOUT_SECONDS`, so set a matching client timeout.


**Body** — [`OriginCheckRequest`](/docs/reference/http-api-models#origincheckrequest)
