# Configuration

The CLI automatically reads `.env` from the project directory. Values already
present in the process environment take precedence, so production services can
continue to use systemd or a secret manager without changing local workflows.

Describes `Settings.from_environment` in `src/blitzecdn/config.py`.

Precedence: environment variable, then the matching key in
`blitzecdn.toml`, then the default. Relative paths resolve against
`BLITZE_PROJECT_DIR` (default: the working directory).

## Operational rules

- Environment values override TOML. Record which layer owns each production
  value so a service-manager override does not surprise an operator.
- Relative paths are resolved once from `BLITZE_PROJECT_DIR`; use explicit
  absolute paths for service deployments.
- Restart the API after changing startup configuration or keys.
- Treat path changes as migrations: stop mutations, copy state with ownership
  intact, update configuration, then run `doctor` and `validate`.
- Rotate API secrets with the [overlap procedure](/docs/operate/api-key-rotation).
- `BLITZE_ORIGIN_CHECK_TIMEOUT_SECONDS` is the per-origin budget for
  [`blitzecdn origin check`](/docs/reference/cli#blitzecdn-origin-check). Keep it
  short: an origin that needs longer than this to accept a TCP connection is one
  the edges will struggle with too.
- `BLITZE_ACME_CA_DOMAIN` is the CA identity a CAA record must name for
  [`cert preflight`](/docs/reference/cli#blitzecdn-cert-preflight) to consider
  issuance permitted. Change it only when `BLITZE_CERTBOT` is pointed at another
  ACME server — a CAA check against the wrong CA is worse than none, because it
  passes while the real CA is refused.

Certificate preflight predicts what the CA will see, and the CA resolves from
the public internet. `BLITZE_PREFLIGHT_DNS_SERVERS` sends its lookups to those
resolvers instead of the controller's own, which matters wherever the host
resolves differently from the public view — a split-horizon zone, an internal
forwarder, or a transparent proxy that claims every hostname. Left unset,
lookups go through the host resolver as before, including `/etc/hosts`.
Addresses only: a hostname here would have to be resolved by the resolver being
bypassed. `blitzecdn doctor` reports which resolver is in use and whether it
answers reserved names it cannot know.

`BLITZE_ALLOW_EMPTY_SITES` is forwarded to the edge as
[`blitzecdn_nginx_allow_empty_sites`](/docs/reference/ansible#blitzecdn_nginx),
where it decides whether a deploy may remove the last managed site. Leave it
`false`. A desired state that has become empty is far more often a controller
pointed at an edge whose sites were never imported than a fleet you meant to
empty, and the edge stops that deploy before it changes the host.

Set it to `true` only for the run that retires an edge's sites deliberately,
then set it back. Because it is an ordinary setting, a value left in
`blitzecdn.toml` silently approves every later deploy — which is the case the
edge check exists to catch.

## Secrets

Secrets are deliberately not valid TOML keys — they are environment-only.

| Environment variable         | Notes                                                                                                                                                                |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BLITZE_API_KEYS`            | Comma-separated `operator:secret`. Each secret needs ≥ 32 characters. Duplicate operators are rejected.                                                              |
| `BLITZE_API_KEY`             | Single unnamed key, registered as operator `default`. Also ≥ 32 characters.                                                                                          |
| `BLITZE_MAXMIND_LICENSE_KEY` | MaxMind license key, for fetching GeoLite2 onto the edges. Authenticates to the account, so it is not a valid TOML key: a `blitzecdn.toml` carrying one is rejected. |

Both MaxMind values are forwarded into the Ansible subprocess environment and
read by `group_vars` with `lookup('env', ...)`, never passed as `--extra-vars`
— argv is readable by every account on the controller. They are set on every
run even when empty, so a stale export in the deploying shell cannot change
what converges.

Set them in `.env`, which `init` and `setup` scaffold with both names commented
out. See [country rules](/docs/reference/records) for the rest of the setup.

## Edge settings

Role variables for the edge fleet live in the control-plane database and are
managed with [`blitzecdn config`](/docs/reference/cli#blitzecdn-config). The
inventory plugin publishes them to every edge at the start of every run:

```bash
blitzecdn config list
blitzecdn config set blitzecdn_nginx_worker_processes 4
blitzecdn config unset blitzecdn_nginx_worker_processes
```

The shipped defaults are still a tracked file,
`ansible/inventory/group_vars/blitzecdn_edges/defaults.yml`. A setting in the
database outranks it; a key you never set falls through to the default.

<Callout type="warning">
  Do not edit `defaults.yml`. It is tracked, and `./install.sh update` refuses
  to run when a tracked file has local changes, so an edit there blocks
  upgrading:

```console
error: tracked files in /opt/blitzecdn have local changes
```

</Callout>

<Callout type="info">
  Keeping overrides in the database rather than in a file beside the defaults is
  what puts the fleet's policy under the same recording, auditing and backup as
  everything else, instead of in a file nothing validates.
</Callout>

Control-plane settings and secrets belong in `.env` instead — the tables above.
The split is the one in the architecture: `.env` configures the control plane,
`blitzecdn config` configures what Ansible does to the edges. Secrets do not go
in either the database or `defaults.yml`; `config set` refuses a name that looks
like a credential.
