# Frequently asked questions

Answers here describe the current release. Where an answer depends on an exact
flag, route or variable, the [reference](/docs/reference/cli) is verified against
the source and is the authority.

## Scope and limits

### Why only Debian and Ubuntu?

Because the same rules are enforced twice — once in Python on the controller and
again by the Ansible roles on the host — and that is only tractable against a
narrow, well-understood platform. Supporting every distribution would mean
either weakening the edge-side checks or maintaining a matrix of them. This
release targets Debian 12+ and Ubuntu 24.04+ edges and commits to them.

### Can BlitzeCDN provision my servers or manage DNS?

No. It does not provision virtual machines, manage DNS, issue wildcard
certificates, or provide active/active job execution. Each of those needs an
explicit provider or distributed-state design, and the release would rather
refuse them than half-implement them. See
[deliberate limits](/docs/understand/architecture#deliberate-limits).

Cache invalidation _is_ supported, but synchronously: `blitzecdn cache purge`
reaches every edge it can and reports which ones purged. An edge that was
unreachable at the time is not retried later, so the purge is reported
incomplete rather than silently queued.

### Why is there only one controller node?

API deployments are handed to Dramatiq through Redis, but the database,
deployment lock, generated state, and certificate store remain local to one
controller. The `fcntl` lock is correct on that node and meaningless across
several. Active/active operation also needs distributed state, locking, and
secret material; a durable queue alone does not make the controller highly
available.

### What does `ansible-runner` do?

BlitzeCDN uses Ansible Runner's Python interface in subprocess mode for runtime
playbook execution. Runner owns the local process lifecycle, timeout, artifacts,
and structured per-host event stream; the roles still implement all hardening. The controller does not
currently use Runner execution environments, and Runner does not make the
single-controller architecture active/active.

## Desired state and validation

### Can I edit desired state by hand?

You can, but it will not get you past the boundary. Every value that can enter
an Nginx template is constrained by immutable domain models on the controller,
and the Ansible roles re-check the same rules against the host. A hand-edited
desired-state file is therefore rejected on the edge rather than silently
applied.

This matters most for certificate paths, which are a privilege boundary rather
than a syntax concern: a deploy copies them onto every edge as root. Domain
models confine them to `/etc/blitzecdn/tls/`, `/etc/ssl/` and
`/etc/letsencrypt/`, reserve the managed `uploaded`/`requested` paths to the
certificate endpoints, and the Nginx role re-checks both rules.

### What is the difference between `validate`, `plan` and `deploy`?

`validate` renders a snapshot and runs syntax checks without contacting hosts.
`plan` runs Ansible in check mode and shows the resulting deployment record.
Interactive `deploy` validates, runs a check-mode preview, asks for confirmation,
then converges the edges. `deploy --yes` skips that interactive validation and
preview for reviewed automation. `doctor` is the one before all of them: it
reports local readiness without touching anything remote.

### How is the control plane / edge contract checked?

The control plane and roles ship together. Contract tests render real desired
state, validate its keys against the role argument specification, and render
the Nginx templates before a release is built.

## Failure behaviour

### What happens if a deployment fails halfway through?

The deployment record settles as `failed` with bounded retained output, and
canonical desired state is left alone — it only advances after a successful
convergence. Nginx is not reloaded after a failed validation, so a bad
configuration does not reach a running server.

### What happens on a timeout?

Ansible Runner enforces the configured timeout and shuts down the playbook
execution it manages. The controller maps that outcome to `timed_out` and keeps
the run log for diagnosis.

Importantly, **a timeout is not proof that no remote changes occurred.** Rerun
`plan` before retrying.

### A deployment is stuck in `queued` or `running`. What now?

API deployments run in a Dramatiq worker, so the record only settles when Ansible
finishes. If the controller restarted mid-run, startup marks the record
`abandoned`. Rerun `plan` before retrying.

Do not delete a live lock file. Filesystem locks release when their owning
process exits.

### What does rollback actually roll back to?

An explicit successful applied snapshot — a state that genuinely ran — not a
reconstruction. Rollback deploys that snapshot and only replaces canonical
desired state after it succeeds, in a single database transaction. Selection,
convergence and replacement all happen under one hold of the deployment lock, so
a concurrent site edit cannot be silently discarded.

## Security

### Are private keys ever readable once uploaded?

No. Uploaded private keys are validated on the way in, then never returned by
the API, never logged, and never included directly in deployment snapshots.
Secrets live in the environment, a secret manager, Ansible Vault, or restrictive
controller state — and are never accepted as CLI arguments, where they would
land in shell history and process listings.

### Do API keys act as roles?

No. API keys authenticate operators; they are not authorization roles. Ten
failed authentications from one client address within a minute are throttled —
note that behind a reverse proxy this counts all clients together unless the
proxy is accounted for.

### How are certificates issued?

Either upload a chain, or issue via ACME HTTP-01 from the controller. Issuance
is centrally coordinated: one controller-side Certbot process runs, and its
hooks use a focused playbook to synchronise the HTTP-01 token to every edge
before validation. Certificates are issued once and distributed from there.

## This site

### How is the reference maintained?

Everything under [Reference](/docs/reference/cli) is maintained as MDX in this
repository. Changes to commands, API routes, configuration, or roles should
update the corresponding page in the same release pull request.

### Which versions does this site document?

The versions named on the individual reference and release pages. Verify those
labels when updating documentation for a new control-plane or edge release.
