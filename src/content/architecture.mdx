# Architecture

## Original system assessment

The original repository combined a global FastAPI application, loosely typed
service functions, a YAML site database, generated YAML, SQLite deployment
records, a Bash/curl helper, and Ansible roles. HTTP background tasks held an
open `fcntl` lock and launched `ansible-playbook`; process restart lost queued
work. Rollback rewrote current YAML before remote convergence. Validation and
defaults were duplicated in Pydantic, YAML serializers, Ansible assertions,
role defaults, and Jinja. Inventory contained real hosts, root SSH, and a
repository-local private-key path. The firewall role was commented out.

## Target boundaries

```text
CLI / authenticated API
          |
          v
application.ControlPlane       workflow, audit, TLS, transitions, rollback
       /             \
      v               v
domain models      infrastructure adapters
invariants         SQLite | atomic files | process lock | Ansible subprocess
                                          |
                                          v
                              declarative Ansible edge roles
```

- `domain` defines immutable CDN site and deployment state plus all values that
  may enter Nginx templates.
- `application` implements use cases and is the sole coordinator of persistence
  and remote execution.
- `infrastructure.database` is the canonical desired-state, deployment-snapshot,
  and audit repository.
- `infrastructure.filesystem` writes an ephemeral, mode-0600 Ansible variable
  file atomically and rejects symlink destinations.
- `infrastructure.ansible` uses an argument array, closed stdin, explicit cwd,
  local temporary directory, timeout, bounded retained output, and a deployment
  lock. It translates OS/process errors at the boundary.
- `infrastructure.process` stops a timed-out child's entire process group. Both
  Ansible and Certbot fan work out across hosts, so signalling only the direct
  child would leave workers mutating remote state after the run was recorded.
- `infrastructure.certificates` validates key pairs, SAN coverage, and validity,
  stores managed key material restrictively, and invokes one controller-side
  Certbot process. Certbot hooks use a focused playbook to synchronize an
  HTTP-01 token to every edge before validation.
- `api` and `cli` translate presentation and exit/status semantics only.
- Ansible performs remote convergence. It contains defensive validation but no
  product workflow decisions.

## Execution flow

Site mutations are validated, committed transactionally to SQLite, and audited.
They do not touch hosts. Validation renders a snapshot and runs syntax checks.
A deployment acquires the lock, records an immutable snapshot, transitions
`queued → running`, renders that snapshot, and invokes Ansible. It then records
`succeeded`, `failed`, or `timed_out` with bounded output. A controller restart
marks unfinished records `abandoned`.

The CLI runs that sequence inline. The API runs it on a worker thread and
returns `202` with the `queued` record, because a convergence outlives any
HTTP client. The original system also used background execution and lost queued
work on restart; this version does not, because the record and its snapshot are
committed before the worker starts and `abandon_running` settles anything the
worker did not finish. The lock is an `fcntl` lock on an open file, so the
worker releases it on the way out. Work that can be rejected before queuing —
no rollback target, a deployment already running — still fails synchronously.

Rollback selects an explicit successful applied snapshot (or the latest
successful state different from current), deploys it, and only after success
replaces canonical desired state in one database transaction. Selection,
convergence, and that replacement all happen under a single hold of the
deployment lock, so a concurrent site edit cannot be silently discarded.

## The control plane / edge contract

The control plane and the edge roles ship as separate repositories, so the
desired-state document they exchange is a versioned interface rather than an
internal detail.

`_write_desired_state` emits `blitzecdn_desired_state_version` alongside
`blitzecdn_nginx_sites`. The Nginx role declares
`blitzecdn_nginx_supported_state_versions` and refuses to run against anything
else, so a version-skewed pair fails before the first host is touched instead
of midway through a 25%-at-a-time rollout. An absent version is caught earlier
still, by the role's `argument_specs`.

Bump `DESIRED_STATE_VERSION` when the shape changes in a way an older role
cannot honour — a new required key, a renamed key, or new semantics for an
existing one. Adding a key older roles can safely ignore does not need a bump.

`tests/test_contract.py` guards the boundary from the control-plane side: it
renders desired state from real `CdnSite` values and asserts that every emitted
key is declared in `argument_specs.yml`, that required keys are present, that
role `choices` cover every domain enum value, and that `site.conf.j2` renders.
It also keeps `tests/fixtures/desired-state.yml` — the document CI feeds to a
real playbook — identical to what the control plane actually produces.

## Security and trust boundaries

API keys authenticate operators but are not authorization roles. Secrets are
kept in environment/secret-manager, Ansible Vault, or restrictive controller
state and are never accepted as CLI arguments. Uploaded private keys are
validated, never returned by the API, and never included directly in deployment
snapshots or logs. SSH host keys are operator-verified. Remote privilege escalation
is explicit per play; global root login is disabled. Domain models constrain
every value inserted into Nginx configuration, including DNS/IP syntax,
durations, ports, names, and absolute certificate paths.

Certificate paths are a privilege boundary, not just a syntax concern: a deploy
copies them onto every edge as root. Domain models confine them to
`/etc/blitzecdn/tls/`, `/etc/ssl/`, and `/etc/letsencrypt/`, and reserve the
managed `uploaded`/`requested` paths to the certificate endpoints. The Nginx
role re-checks both rules, so a hand-edited desired-state file cannot bypass
them either.

## Extension points

Add a provider by implementing a focused infrastructure adapter and invoking it
from a use case; provider details must not enter domain site validation. Add a
remote responsibility as a namespaced, argument-specified Ansible role. Add a
workflow in `ControlPlane`, then expose it independently through CLI/API.

## Deliberate limits

This release supports one controller node, Debian/Ubuntu edges, Nginx, UFW,
existing/uploaded certificates, and centrally coordinated HTTP-01 issuance. It
does not provision virtual machines, manage DNS, issue wildcard certificates,
distribute cache invalidations, or provide active/active job execution. Those
require explicit provider and distributed-state designs.

## Dependency decisions

Typer provides nested CLI commands, validation-friendly annotations, and stable
automation help without maintaining a parser framework. Pydantic is limited to
configuration/domain boundary validation and immutable serialization. Standard
library logging, `sqlite3`, `pathlib`, `tomllib`, and `subprocess` avoid adapters
whose lifecycle or global configuration would obscure safety controls.
`ansible-runner` was not selected because BlitzeCDN needs one local playbook
process and explicit command, timeout, output, and lock semantics; its event and
container features would add state without replacing the distributed job queue
that multi-controller operation actually requires.
